1. INTRODUCTION ET RESULTAT OBTENU
-----------------------------------------------------------------------
TaskManager est une application PHP MVC utilisant MariaDB. Ce laboratoire
fait tourner l'application dans une VM Ubuntu Server hébergée par
VirtualBox sur Windows. Terraform décrit la VM ; Ansible installe les
services, configure la base et copie l'application.

Résultat vérifié :
  - VM Ubuntu 22.04.5 LTS démarrée dans VirtualBox.
  - Accès réseau entre Windows, Kali et Ubuntu.
  - Ansible depuis Kali s'est connecté à Ubuntu par SSH.
  - Apache, PHP et MariaDB ont été installés/configurés.
  - Ansible a déployé l'application et initialisé la base.
  - Depuis Kali, `curl -I http://192.168.56.102/taskmanager/public/`
    a renvoyé `HTTP/1.1 200 OK`.

Jenkins est installé sur Kali. Le job `taskmanager-deploy` récupère le
dépôt GitHub, exécute les validations, puis déploie sur Ubuntu avec
Ansible lorsque toutes les validations réussissent. Le build #3 a
réussi, y compris l'étape de déploiement. Les nouveaux commits de la
branche `main` sont détectés périodiquement par Jenkins.


2. ARCHITECTURE ET RESEAU DES TROIS MACHINES
-----------------------------------------------------------------------

Machine       Rôle                         Réseau / adresse observée
------------- ---------------------------- --------------------------
Windows       Hôte VirtualBox, Terraform   Host-only : 192.168.56.1
Kali          Administration, Jenkins,     NAT : 10.0.2.15
              Prometheus, Grafana           Host-only : 192.168.56.11
Ubuntu        Application, MariaDB,        Host-only : 192.168.56.102
              Node Exporter                NAT : 10.0.2.15

Le réseau privé VirtualBox s'appelle :
  VirtualBox Host-Only Ethernet Adapter

Les informations de VirtualBox observées :
  - Adresse hôte Host-only : 192.168.56.1
  - Masque : 255.255.255.0 (/24)
  - DHCP VirtualBox activé dans `VBoxManage list dhcpservers`
  - Adresse serveur DHCP : 192.168.56.100
  - Plage observée : 192.168.56.101 à 192.168.56.254
  - Ubuntu a reçu 192.168.56.102 sur eth0 (Host-only).

Kali a deux cartes :
  - eth0 : NAT VirtualBox, adresse observée 10.0.2.15.
  - eth1 : Host-only, adresse observée 192.168.56.11/24.

La VM Ubuntu a deux cartes :
  - eth0 : Host-only, utilisée pour SSH depuis Kali et HTTP vers le site.
  - eth1 : NAT VirtualBox, utilisée par Ubuntu pour accéder à Internet.
    Après création, eth1 était inactive au premier lancement Ansible.
    Elle a été activée manuellement avec `ip link` et a reçu 10.0.2.15
    par DHCP. L'accès APT a ensuite fonctionné.

Host-only et NAT répondent à des besoins différents :
  - Host-only fait communiquer les machines de l'hôte et les VM sur le
    réseau privé VirtualBox ; ce n'est pas, à lui seul, une connexion
    Internet.
  - NAT donne à Ubuntu un accès sortant à Internet via Windows, sans
    rendre directement la VM accessible depuis Internet.
  - Le DHCP attribue automatiquement une adresse ; il ne remplace pas
    SSH et ne donne pas de droit de connexion.

Commandes de diagnostic sous Windows (PowerShell) :
  & "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" list hostonlyifs
  & "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" list dhcpservers
  & "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe" list vms

Commandes de diagnostic dans Kali ou Ubuntu :
  ip -br addr
  ip route
  ping -c 3 192.168.56.1
  ping -c 3 192.168.56.102

Les adresses 10.0.2.15 sont affectées indépendamment à Kali et à Ubuntu
par leurs réseaux NAT VirtualBox respectifs ; elles ne désignent pas le
même hôte. Pour SSH/Ansible et le site, utiliser l'adresse Host-only
d'Ubuntu (192.168.56.102). L'adresse Host-only de Kali est
192.168.56.11. Vérifier avec `ip -br addr` après redémarrage, car les
adresses DHCP peuvent changer.

Liaison logique des trois machines et des services :

  Windows (192.168.56.1)
    |-- navigateur --> Grafana sur Kali (192.168.56.11:3000)
    |-- navigateur --> Jenkins sur Kali (192.168.56.11:8080)
    |-- navigateur --> TaskManager sur Ubuntu (192.168.56.102:80)
    |
    +---- réseau Host-only 192.168.56.0/24 -------------------------+
                                                                  |
  Kali (192.168.56.11) -- SSH/Ansible, TCP 22 ----------------> Ubuntu
       |                                                          |
       +-- Prometheus scrapes Node Exporter Kali :9100            |
       +-- Prometheus scrapes Node Exporter Ubuntu :9100 ---------+
       +-- Grafana interroge Prometheus sur localhost:9090

Le réseau Host-only `192.168.56.0/24` est directement connecté aux
interfaces privées des machines : il permet les échanges Windows/Kali/
Ubuntu sans passer par Internet. La route par défaut Internet des VM
passe par leur interface NAT VirtualBox ; l'adresse de passerelle
effective n'a pas été relevée dans les sorties conservées et doit être
lue avec `ip route` sur chaque VM. Les deux adresses NAT identiques
`10.0.2.15` sont dans des réseaux NAT VirtualBox séparés, elles ne
permettent donc pas à Kali de joindre Ubuntu. Les services et
communications du laboratoire utilisent les adresses Host-only.

Ports et sens des communications observés/configurés :
  - Windows -> Kali TCP 3000 : interface Web Grafana.
  - Windows -> Kali TCP 8080 : interface Web Jenkins.
  - Windows/Kali -> Ubuntu TCP 80 : application TaskManager/Apache.
  - Kali/Jenkins -> Ubuntu TCP 22 : SSH et déploiement Ansible.
  - Prometheus sur Kali -> TCP 9100 de Kali et Ubuntu : collecte Node
    Exporter. L'interface Prometheus est consultée localement sur Kali
    au port 9090 ; Grafana utilise `http://localhost:9090`.

5. TERRAFORM : CONFIGURATION, COMMANDES ET FICHIERS GENERES
-----------------------------------------------------------------------

Extrait essentiel de terraform/main.tf :

  terraform {
    required_version = ">= 1.5.0"
    required_providers {
      virtualbox = {
        source  = "terra-farm/virtualbox"
        version = "0.2.2-alpha.1"
      }
    }
  }

  resource "virtualbox_vm" "taskmanager" {
    name   = var.vm_name
    image  = "https://vagrantcloud.com/bento/boxes/ubuntu-22.04/versions/202510.26.0/providers/virtualbox/amd64/vagrant.box"
    cpus   = var.vm_cpus
    memory = "${var.vm_memory_mib} mib"
    network_adapter { type = "nat" }
    network_adapter {
      type           = "hostonly"
      host_interface = var.hostonly_interface
    }
  }

Configuration locale attendue dans terraform/terraform.tfvars :
  hostonly_interface = "VirtualBox Host-Only Ethernet Adapter"

Paramètres par défaut :
  vm_name       = taskmanager-ubuntu
  vm_cpus       = 2
  vm_memory_mib = 2048

Procédure normale depuis PowerShell sur Windows :

  Set-Location C:\Users\Ali.KONE\Downloads\test\taskmanager
  Copy-Item terraform\terraform.tfvars.example terraform\terraform.tfvars
  notepad terraform\terraform.tfvars
  Set-Location terraform
  terraform init
  terraform fmt -check
  terraform validate
  terraform plan
  terraform apply

Avant de confirmer `terraform apply`, vérifier le plan : il doit annoncer
les changements attendus. Pour afficher la sortie après un apply réussi :
  terraform output -raw taskmanager_ip

But des principales commandes :
  init       Télécharge le fournisseur et crée le verrou de dépendances.
  fmt        Vérifie le format HCL.
  validate   Vérifie la syntaxe et la cohérence de configuration.
  plan       Prévisualise les changements sans les appliquer.
  apply      Crée/modifie les ressources après confirmation.
  output     Affiche une sortie calculée par Terraform.
  destroy    Supprime les ressources gérées ; action destructive.

Fichiers générés :
  .terraform/                 fournisseur téléchargé (non versionné)
  .terraform.lock.hcl         verrou de version (à versionner normalement)
  terraform.tfstate           inventaire local réel des ressources
  terraform.tfstate.backup    état précédent
  terraform.tfvars            paramètres locaux non versionnés
  vagrant.box                 image téléchargée par le fournisseur

Incident effectivement rencontré :
  1. Première erreur : VBoxManage introuvable dans PATH. Le chemin
     VirtualBox a été ajouté temporairement au PATH PowerShell.
  2. Ensuite, Terraform a créé la VM puis le fournisseur a échoué en
     lisant ses informations réseau :
       No match with get guestproperty output
  3. La VM a bien démarré et reçu l'adresse Host-only 192.168.56.102.
  4. L'état Terraform actuel contient l'ID de VM
     22a003ab-b0d4-4f56-82ff-12164eff6e83 et le statut "tainted".
     L'output taskmanager_ip n'a pas été produit.
  5. Ce fournisseur attend des propriétés d'adresse IP invitées qui
     n'ont pas été exposées comme il l'attendait ; la VM, elle, tournait.

ATTENTION : état tainted = Terraform peut vouloir remplacer la VM au
prochain apply. Sauvegarder d'abord la base et réconcilier l'état ; ne
pas utiliser apply/destroy par réflexe. Ne jamais supprimer le state
pour "réparer" Terraform sans comprendre les conséquences.


6. SSH : ROLE ET FONCTIONNEMENT DES CLES SUR KALI ET UBUNTU
-----------------------------------------------------------------------

Le réseau permet d'atteindre une machine ; SSH vérifie l'identité et les
droits de l'utilisateur. Un ping qui répond ne prouve pas qu'un accès
SSH est autorisé.

Trois éléments SSH à distinguer :

  A. Clé privée du client Kali
     Fichier utilisé pour prouver l'identité de l'utilisateur vagrant :
       ~/.ssh/vagrant_insecure_private_key
     Elle doit rester privée et avoir les permissions 600.

  B. Clé publique autorisée sur Ubuntu
     La clé publique correspondante est déjà présente dans le compte
     vagrant de cette image de laboratoire. Le serveur compare la clé
     présentée par Kali aux clés autorisées du compte.

  C. Clé d'hôte SSH d'Ubuntu
     Créée par le serveur SSH pour identifier Ubuntu auprès des clients.
     Kali l'a enregistrée dans ~/.ssh/known_hosts après confirmation
     initiale. Elle est différente de la clé privée utilisateur.

La clé Vagrant récupérée est volontairement publique et non sécurisée.
Elle ne protège pas une machine : n'utiliser que pour le laboratoire,
ne jamais la réutiliser sur une machine personnelle/production, et ne
jamais la committer dans Git.

Commandes exécutées dans Kali (depuis n'importe quel dossier) :
  mkdir -p ~/.ssh
  curl -fsSL https://raw.githubusercontent.com/hashicorp/vagrant/main/keys/vagrant -o ~/.ssh/vagrant_insecure_private_key
  chmod 600 ~/.ssh/vagrant_insecure_private_key

La clé est enregistrée dans /home/<utilisateur-kali>/.ssh/ ; le dossier
courant du terminal n'a pas d'importance.

Connexion manuelle :
  ssh -i ~/.ssh/vagrant_insecure_private_key vagrant@192.168.56.102

La première connexion demande de confirmer l'empreinte du serveur.
Ne confirmer que si l'on sait qu'il s'agit bien de la VM Ubuntu attendue.
Fermer la session distante :
  exit

Pour créer une vraie clé personnelle (amélioration future, ne remplace
pas automatiquement la clé de ce laboratoire) :
  ssh-keygen -t ed25519 -f ~/.ssh/taskmanager_ed25519
Puis installer la clé publique sur un serveur contrôlé :
  ssh-copy-id -i ~/.ssh/taskmanager_ed25519.pub utilisateur@IP
La clé privée taskmanager_ed25519 ne doit jamais être copiée sur Ubuntu
ni partagée. Une nouvelle clé ne fonctionnera qu'après autorisation de
sa clé publique sur le serveur.


7. ANSIBLE : INVENTAIRE, PLAYBOOK, ROLE ET DEPLOIEMENT
-----------------------------------------------------------------------

Ansible est installé et lancé depuis Kali. Ubuntu est la machine cible.
Ansible utilise SSH, l'utilisateur vagrant et sudo (become: true).

Inventaire (exemple à garder à jour) :
  [web]
  taskmanager ansible_host=192.168.56.102 ansible_user=vagrant

  [web:vars]
  ansible_python_interpreter=/usr/bin/python3

L'inventaire fourni dans le dépôt conserve l'adresse de secours
192.168.56.101 et ne fixe pas de chemin de clé SSH. Cela permet à
Jenkins de fournir le chemin temporaire de la clé à partir du credential.
Pour les exécutions manuelles depuis Kali, indiquer la clé explicitement
avec `--private-key ~/.ssh/vagrant_insecure_private_key`.
Pour Jenkins, TASKMANAGER_HOST remplace l'adresse d'exemple et le
credential SSH fournit la clé privée.

Installation/dépendances dans Kali :
  sudo apt update
  sudo apt install -y ansible git python3-pymysql
  ansible-galaxy collection install -r ansible/requirements.yml

Test de connexion (exécuté avec succès) :
  ansible -i ansible/inventory.ini web -m ping --private-key ~/.ssh/vagrant_insecure_private_key
Résultat obtenu : SUCCESS, "ping": "pong".

Déploiement (exécuté avec succès) :
  ansible-playbook -i ansible/inventory.ini ansible/site.yml --private-key ~/.ssh/vagrant_insecure_private_key

Le playbook demande deux fois taskmanager_db_password sans afficher
la saisie. Il faut entrer le même secret, hexadécimal d'au moins 32
caractères. Pour en générer un :
  openssl rand -hex 24
Garder le secret dans un gestionnaire sûr ; ne pas le mettre dans Git ou
dans ce document.

Actions du rôle taskmanager :
  1. Valide le format du mot de passe.
  2. Installe Apache, PHP, MariaDB et le pilote Python MariaDB.
  3. Active et démarre MariaDB.
  4. Crée la base taskmanager.
  5. Copie puis importe database/schema.sql.
  6. Crée l'utilisateur SQL restreint taskmanager.
  7. Copie app/, config/, database/ et public/ sous
     /var/www/html/taskmanager/.
  8. Configure les variables DB pour Apache et redémarre Apache.

Problème APT résolu :
  Au premier lancement, eth1 (NAT) était inactive. Dans Ubuntu :
    sudo ip link set eth1 up
    sudo dhclient -v eth1
  Ubuntu a reçu 10.0.2.15 avec route par défaut 10.0.2.2 ; `apt-get
  update` a alors fonctionné. Cette activation manuelle peut ne pas
  persister après redémarrage. À améliorer en configurant le réseau
  Ubuntu de façon persistante.

Le playbook s'est terminé avec :
  ok=15 changed=11 unreachable=0 failed=0

Avertissements observés, sans échec du déploiement :
  - groupe et hôte tous deux nommés taskmanager dans inventory.ini ;
    renommer par exemple le groupe [web] et adapter hosts: web.
  - modules community.mysql.mysql_db/mysql_user dépréciés dans la
    version de collection utilisée ; suivre la documentation de la
    collection et migrer vers les noms de modules actuels.

Test HTTP effectué depuis Kali :
  curl -I http://192.168.56.102/taskmanager/public/
Résultat : HTTP/1.1 200 OK, Apache/2.4.52 (Ubuntu).
URL navigateur :
  http://192.168.56.102/taskmanager/public/


8. MARIADB : ACCES ET COMMANDES SQL PRATIQUES
-----------------------------------------------------------------------

La base de production/laboratoire se trouve sur Ubuntu. Connexion
administrateur depuis la console Ubuntu :
  sudo mariadb taskmanager

Commandes SQL utiles (à saisir dans l'invite MariaDB, avec ; final) :
  SHOW TABLES;
  DESCRIBE tasks;
  SELECT * FROM tasks;

Insérer une tâche :
  INSERT INTO tasks (title, description, status)
  VALUES ('Tester MariaDB', 'Ajout depuis la console', 'todo');

Vérifier :
  SELECT * FROM tasks;

Quitter le client :
  exit

Cette méthode utilise le compte système root via le socket local et ne
nécessite pas de rendre MariaDB accessible depuis le réseau.

Une connexion depuis Kali peut se faire plus tard par tunnel SSH, sans
exposer directement le port MariaDB 3306 :

Terminal Kali 1 (laisser ouvert) :
  ssh -N -L 3307:127.0.0.1:3306 -i ~/.ssh/vagrant_insecure_private_key vagrant@192.168.56.102

Terminal Kali 2 :
  sudo apt install -y mariadb-client
  mariadb -h 127.0.0.1 -P 3307 -u taskmanager -p taskmanager

Saisir le mot de passe taskmanager choisi pour le playbook. Fermer le
tunnel avec Ctrl+C dans le premier terminal.

    MariaDB locale de tests, Terraform Linux et Ansible.
  - Récupère le dépôt depuis GitHub ; Ansible établit ensuite la
    connexion SSH vers Ubuntu via Host-only.

Ubuntu :
  - Héberge l'application web, Apache/PHP et MariaDB de l'application.
  - N'héberge ni Jenkins ni le dépôt Git de travail.
  - Reçoit les fichiers applicatifs par Ansible/SSH après les tests.

Flux à chaque changement de code :
  développeur -> git push vers GitHub/main
  Jenkins/Kali -> interroge GitHub, clone/actualise le workspace
  Jenkinsfile -> syntaxe PHP -> PHPStan -> PHPUnit -> Terraform validate
                 -> syntaxe Ansible -> déploiement Ansible sur Ubuntu
  Ubuntu -> application mise à jour, base de données conservée

Le push GitHub ne copie pas directement des fichiers sur Ubuntu.
GitHub héberge la source ; Jenkins récupère le commit et le Jenkinsfile
décrit les contrôles et l'étape de déploiement. L'étape Ansible copie
app/, config/, database/ et public/ vers
/var/www/html/taskmanager/ puis met à jour la configuration si besoin.
Terraform n'est pas utilisé pour déployer le code et Jenkins n'exécute
ni `terraform apply` ni `terraform destroy`.

9.3. Installation de Terraform pour le job Jenkins sur Kali

Terraform présent sur Windows n'est pas automatiquement disponible dans
Kali. Le Jenkinsfile vérifie aussi la configuration Terraform sur son
agent Linux ; Terraform a donc été installé séparément sur Kali.
Version installée et vérifiée : v1.16.6 linux_amd64.

Commandes utilisées dans Kali :
  sudo apt update
  sudo apt install -y unzip
  TF_VERSION=1.16.6
  cd /tmp
  curl -fsSLO "https://releases.hashicorp.com/terraform/${TF_VERSION}/terraform_${TF_VERSION}_linux_amd64.zip"
  curl -fsSLO "https://releases.hashicorp.com/terraform/${TF_VERSION}/terraform_${TF_VERSION}_SHA256SUMS"
  grep " terraform_${TF_VERSION}_linux_amd64.zip$" "terraform_${TF_VERSION}_SHA256SUMS" | sha256sum -c -
  unzip -o "terraform_${TF_VERSION}_linux_amd64.zip" -d /tmp/terraform-install
  sudo install -m 0755 /tmp/terraform-install/terraform /usr/local/bin/terraform
  terraform version
  sudo -u jenkins /usr/local/bin/terraform version
  sudo -u jenkins sh -lc 'command -v terraform'

La vérification SHA256 a réussi. Le binaire `/usr/local/bin/terraform`
est accessible au compte Jenkins. `terraform init -backend=false` dans
le pipeline télécharge son fournisseur dans le workspace Jenkins pour
validation, mais ne crée pas la VM.

9.4. Base de tests Jenkins sur Kali (distincte d'Ubuntu)

PHPUnit ouvre la connexion PDO configurée par DB_HOST, DB_NAME, DB_USER
et DB_PASSWORD. Le pipeline définit DB_HOST=127.0.0.1 et
DB_NAME=taskmanager ; le compte `taskmanager-ci-db` fournit les
variables DB_USER et DB_PASSWORD.

La base de test locale a été initialisée à partir du même schéma SQL du
dépôt, sur le serveur MariaDB de Kali (version 11.8.9 observée). Elle
est indépendante de la base `taskmanager` qui héberge les tâches sur
Ubuntu :
  sudo apt install -y php-cli php-curl php-mbstring php-mysql php-xml mariadb-server
  sudo systemctl enable --now mariadb
  cd ~/Documents/taskmanager
  sudo mariadb < database/schema.sql

Dans l'invite MariaDB Kali, l'utilisateur dédié a été créé avec des
droits limités à la base de test :
  CREATE USER 'taskmanager_ci'@'127.0.0.1'
    IDENTIFIED BY 'MOT_DE_PASSE_DE_TEST';
  GRANT ALL PRIVILEGES ON taskmanager.*
    TO 'taskmanager_ci'@'127.0.0.1';

Le mot de passe réel n'est pas documenté. L'accès local administrateur
`sudo mariadb` n'a pas demandé de mot de passe parce que MariaDB utilise
l'authentification système/socket pour root. Le compte applicatif
`taskmanager_ci`, lui, possède son propre mot de passe.

Le premier CREATE USER avait renvoyé ERROR 1396 car l'utilisateur avait
déjà été créé lors de la commande précédente, d'abord avec un texte
indicatif de remplacement. Le mot de passe a ensuite été changé avec :
  ALTER USER 'taskmanager_ci'@'127.0.0.1'
    IDENTIFIED BY 'NOUVEAU_MOT_DE_PASSE_DE_TEST';
  FLUSH PRIVILEGES;

La connexion a été testée exactement avec le compte système du job :
  sudo -u jenkins mariadb -h 127.0.0.1 -u taskmanager_ci -p taskmanager -e "SELECT 1;"
Résultat observé : une valeur `1`.

Credential Jenkins :
  ID       : taskmanager-ci-db
  Type     : Username with password
  Username : taskmanager_ci
  Password : secret du compte de test Kali
Importance: injecté seulement dans l'étape PHPUnit afin que les tests
            PDO puissent se connecter à la base locale.

Le test PHPUnit qui vide la table tasks doit utiliser uniquement cette
base de test ; ne jamais faire pointer le credential vers la base

9.5. SSH et credentials de déploiement

Le réseau Host-only rend Ubuntu joignable depuis Kali mais ne dispense
pas d'authentification SSH. Ubuntu accepte pour ce laboratoire le compte
`vagrant` et la clé privée Vagrant fournie avec l'image Bento. Cette clé
est connue publiquement ; elle ne convient qu'au réseau de laboratoire.

La clé privée utilisateur du client Kali :
  ~/.ssh/vagrant_insecure_private_key
Elle sert à prouver l'identité de `vagrant`. Elle n'est pas la clé
d'hôte SSH Ubuntu. La clé publique correspondante est déjà autorisée
dans la VM de laboratoire.

La clé d'hôte ED25519 d'Ubuntu sert à Kali/Jenkins à vérifier qu'ils
parlent bien à cette VM. Son empreinte a été comparée entre Ubuntu et
Kali avant son installation dans le known_hosts système Jenkins.

Commandes de vérification effectuées :
  # Dans la console Ubuntu
  sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

  # Dans Kali, comparer l'empreinte réseau à celle affichée par Ubuntu
  ssh-keyscan -t ed25519 192.168.56.102 > /tmp/taskmanager-hostkey
  ssh-keygen -lf /tmp/taskmanager-hostkey

Après comparaison manuelle des empreintes :
  sudo install -d -o jenkins -g jenkins -m 700 /var/lib/jenkins/.ssh
  sudo install -o jenkins -g jenkins -m 600 \
    /tmp/taskmanager-hostkey \
    /var/lib/jenkins/.ssh/known_hosts
  sudo -u jenkins ssh-keygen -F 192.168.56.102 \
    -f /var/lib/jenkins/.ssh/known_hosts

Le test a trouvé l'entrée de 192.168.56.102. Ne pas accepter
automatiquement une nouvelle empreinte si l'adresse DHCP change : la
comparer à nouveau depuis la console Ubuntu.

Credentials Jenkins créés dans le domaine global System :

  ID: taskmanager-ci-db
    Type : Username with password
    Rôle : authentification MySQL/MariaDB des tests PHPUnit sur Kali.

  ID: taskmanager-ubuntu-ssh
    Type : SSH Username with private key
    Username : vagrant
    Private key : contenu complet de
      ~/.ssh/vagrant_insecure_private_key
    Rôle : permettre au pipeline d'ouvrir SSH vers Ubuntu.

  ID: taskmanager-ubuntu-db-password
    Type : Secret text
    Secret : mot de passe DB `taskmanager` de la VM Ubuntu
    Rôle : permettre au rôle Ansible de définir/réconcilier l'utilisateur
      SQL applicatif sans invite interactive.

Les trois credentials sont conservés par Jenkins, pas dans Git. Ils
doivent rester distincts : mot de passe tests Kali, clé SSH Ubuntu,
mot de passe SQL Ubuntu. Ne jamais copier les valeurs réelles dans cette
documentation ou la sortie console.

Le Jenkinsfile lie les credentials avec :
  withCredentials([usernamePassword(credentialsId: 'taskmanager-ci-db', ...)])
  sshUserPrivateKey(credentialsId: 'taskmanager-ubuntu-ssh', ...)
  string(credentialsId: 'taskmanager-ubuntu-db-password', ...)

Pendant le déploiement, le shell crée un fichier JSON temporaire avec
permissions 600 contenant l'IP cible et le mot de passe Ansible,
désactive l'écho des commandes, puis le supprime avec un trap de sortie.
Ansible reçoit la clé du credential via `--private-key "$SSH_KEY"` ;
aucun fichier de clé fixe dans le workspace n'est requis.

9.7. Déroulement détaillé du Jenkinsfile

  pipeline { agent any }
    Exécute sur le nœud Jenkins principal de Kali. C'est pratique pour
    ce labo ; pour un vrai serveur, un agent distinct est préférable.

  triggers { pollSCM('H/2 * * * *') }
    Interroge périodiquement le SCM GitHub pour détecter les nouveaux
    commits. Les commits détectés sur la branche configurée déclenchent
    le job sans clic Build Now. Cela n'est pas un webhook et peut avoir
    jusqu'à environ deux minutes de délai.

  environment
    TF_IN_AUTOMATION=true évite les interactions Terraform.
    DB_HOST=127.0.0.1 et DB_NAME=taskmanager ciblent la base tests Kali.
    TASKMANAGER_HOST=192.168.56.102 est l'adresse Host-only Ubuntu
    actuellement observée ; actualiser si DHCP la change.

Stages exécutés dans l'ordre :

  1. PHP syntax
     `find ... -name '*.php'` passe chaque fichier PHP à `php -l`.
     Une erreur de syntaxe arrête le pipeline.

  2. PHPStan
     Télécharge phpstan.phar s'il manque, puis analyse avec phpstan.neon.
     Une erreur statique arrête les étapes suivantes.

  3. PHPUnit
     Injecte le credential taskmanager-ci-db sous DB_USER/DB_PASSWORD,
     télécharge phpunit.phar s'il manque, lance les tests sur la DB Kali.
     Les identifiants sont masqués par Jenkins autant que possible.

  4. Terraform validation
     `terraform fmt -check -recursive` vérifie le format ;
     `terraform init -backend=false -input=false` initialise les
     fournisseurs sans backend distant ;
     `terraform validate` vérifie la configuration.
     Aucun `plan`, `apply` ou `destroy` n'est lancé.

  5. Ansible syntax
     Installe les collections déclarées dans ansible/requirements.yml
     pour le compte Jenkins, puis exécute --syntax-check sur site.yml.

  6. Deploy to Ubuntu
     N'est exécuté que si les cinq stages précédents réussissent.
     Lie la clé SSH et le secret de DB Ubuntu depuis Credentials.
     Lance `ansible-playbook -i ansible/inventory.ini ansible/site.yml`
     avec la clé temporaire du credential et les extra-vars.
     Le playbook installe/actualise l'application et redémarre Apache
     seulement si la configuration change.

La synchronisation applicative n'efface pas la VM ni sa base. Le rôle
ne copie que app/, config/, database/ et public/. Les données SQL sont
gérées dans MariaDB sur Ubuntu, séparément des fichiers GitHub.

9.8. Premier échec SSH puis correction et succès

Build initial :
  Checkout SCM, PHP syntax, PHPStan, PHPUnit, validation Terraform et
  syntaxe Ansible ont réussi. Le déploiement Ansible a échoué avec :
    no such identity: /var/lib/jenkins/.ssh/vagrant_insecure_private_key
    Permission denied (publickey,password).

Cause :
  ansible/inventory.ini contenait alors
  `ansible_ssh_private_key_file=~/.ssh/vagrant_insecure_private_key`.
  Dans le contexte Jenkins, ~ désignait /var/lib/jenkins ; la clé
  n'existait pas à ce chemin. Cette variable d'inventaire prenait
  priorité sur la clé temporaire du credential passée par Jenkins.

Correction :
  supprimer ansible_ssh_private_key_file de l'inventaire versionné ;
  garder `ansible_host` et `ansible_user` dans inventory.ini ;
  fournir la clé Jenkins uniquement par `--private-key`.
  Le groupe de l'inventaire s'appelle maintenant `web`, distinct du
  nom d'hôte `taskmanager`, et site.yml cible `hosts: web`.
  Les commandes Ansible manuelles depuis Kali doivent ajouter :
    --private-key ~/.ssh/vagrant_insecure_private_key

La correction a été poussée sur GitHub/main. Le build #3 a ensuite
terminé en succès en environ 1 minute 3 secondes ; toutes les étapes,
y compris Deploy to Ubuntu, étaient vertes.

Des messages de dépréciation community.mysql.mysql_db/mysql_user ont
été affichés. Ils n'étaient pas l'origine de l'échec SSH et n'ont pas
empêché le build réussi. Il faudra migrer ces modules à terme.

12.1. Architecture et rôle des composants
.......................................................................

La supervision est indépendante du pipeline Jenkins :

  Windows (navigateur)
      | HTTP Host-only :3000
      v
  Kali : Grafana 13.2.4
      | datasource Prometheus : http://localhost:9090
      v
  Kali : Prometheus
      | collecte périodique HTTP /metrics sur TCP 9100
      +---------------------------> Node Exporter Kali
      +---------------------------> Node Exporter Ubuntu
                                      192.168.56.102:9100

  Ubuntu : Apache/PHP/MariaDB + TaskManager

Node Exporter expose un endpoint texte `/metrics` ; il ne pousse pas
les données et ne les conserve pas. Prometheus interroge cet endpoint
selon son `scrape_interval`, puis stocke les séries temporelles sur Kali.
Grafana interroge Prometheus et présente les résultats sous forme de
graphiques. Le navigateur Windows ne collecte ni ne stocke les métriques.

Les métriques système couvrent notamment CPU, mémoire, systèmes de
fichiers, réseau et disponibilité des cibles. L'installation réalisée
ne mesure pas directement les requêtes HTTP Apache, les temps de réponse
TaskManager ni les requêtes MariaDB ; des exporters ou sondes dédiés
seraient nécessaires pour ces mesures applicatives.

12.2. Installation et activation de Prometheus sur Kali
.......................................................................

Prometheus a été installé depuis les dépôts Kali et le service, initialement
inactif, a été activé :

  sudo apt update
  sudo apt install prometheus
  sudo systemctl enable --now prometheus
  systemctl status prometheus --no-pager
  curl -fsS http://localhost:9090/-/ready

Résultat : le service est `active (running)` et `/-/ready` renvoie
`Prometheus Server is Ready.` La requête `curl -I` avait retourné HTTP
405 parce qu'elle envoyait une méthode HEAD ; l'endpoint accepte GET,
utilisé dans la commande de contrôle ci-dessus.

12.3. Installation de Node Exporter sur Ubuntu depuis Kali
.......................................................................

La clé SSH du laboratoire reste sur Kali. La connexion et les commandes

Le résultat comprenait, entre autres, `apt_upgrades_pending` et des

Les lignes `# HELP` décrivent les métriques, `# TYPE` indique leur type,

12.6. Installation et démarrage de Grafana sur Kali
.......................................................................

Le paquet Grafana n'était pas dans les dépôts Kali configurés. Le dépôt
officiel APT a été ajouté avec une clé de signature dédiée, puis le
paquet installé :

  sudo apt install -y wget gpg
  sudo install -d -m 0755 /etc/apt/keyrings
  wget -qO- https://apt.grafana.com/gpg.key | \
    gpg --dearmor | sudo tee /etc/apt/keyrings/grafana.gpg >/dev/null
  sudo chmod 644 /etc/apt/keyrings/grafana.gpg
  echo "deb [signed-by=/etc/apt/keyrings/grafana.gpg] \
    https://apt.grafana.com stable main" | \
    sudo tee /etc/apt/sources.list.d/grafana.list
  sudo apt update
  sudo apt install grafana
  sudo systemctl daemon-reload
  sudo systemctl enable --now grafana-server
  systemctl status grafana-server --no-pager

La version installée rapportée par l'API est 13.2.4. L'installation a
téléchargé environ 381 Mo et estimé 1 377 Mo d'espace nécessaire. Le
service n'a pas été démarré automatiquement par le paquet ; `enable
--now` l'a démarré et activé au démarrage. Le contrôle suivant a réussi :

  curl -fsS http://192.168.56.11:3000/api/health

Résultat :

  database: ok
  version: 13.2.4

L'interface a été ouverte depuis Windows à :
  http://192.168.56.11:3000

La page de connexion initiale a demandé les identifiants Grafana. Après
connexion, Grafana affichait son accueil sans tableau de bord, ce qui est
normal avant d'en créer un. L'accès HTTP du labo n'est pas chiffré ; ne
pas exposer le port 3000 à Internet. Vérifier dans
`/etc/grafana/grafana.ini` la valeur effective de `http_addr` et la
configuration réseau avant tout usage hors du Host-only.

12.8. Vérification des données et requête CPU
.......................................................................

Dans **Explore**, source `prometheus`, mode **Code**, la requête PromQL :

  up

a retourné trois séries avec la valeur `1` :

  up{instance="localhost:9090", job="prometheus"} 1
  up{instance="localhost:9100", job="node"} 1
  up{instance="192.168.56.102:9100", job="ubuntu"} 1

La valeur 1 signifie que la dernière collecte de la cible a réussi ; 0
signale une cible indisponible lors de la collecte. Le graphique conserve
l'historique de la période affichée, ainsi une ancienne chute à 0 peut
coexister avec une valeur courante à 1. Des valeurs courantes à 1 ont
été confirmées pour les trois cibles.

Pourcentage estimé de CPU non-idle par instance, moyenne sur les cœurs,
sur une fenêtre de cinq minutes :

  100 * (1 - avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  ))

Au moment de la capture, le tableau de résultats affichait environ :
  - Ubuntu (192.168.56.102:9100) : 1,83 %.
  - Kali (localhost:9100) : 12,74 %.

Ce sont des mesures instantanées de ce laboratoire, susceptibles de
varier selon les processus actifs. Un pic antérieur autour de 90 % a
baissé après l'installation et le lancement des services ; il ne s'agit
pas d'un seuil d'alerte configuré.

12.9. Espace disque et exploitation
.......................................................................

Après installation de Grafana, `df -h /` a indiqué un disque de 29 Go,
26 Go utilisés et 1,5 Go disponibles (95 %). L'espace disponible doit
être surveillé, notamment pour Prometheus qui conserve ses séries
temporelles sur Kali. Vérification :

  df -h /
  sudo du -sh /var/lib/prometheus /var/lib/grafana 2>/dev/null

Ne pas lancer `apt autoremove` sans examiner d'abord la simulation et
la liste des paquets ; Kali proposait des dépendances de plusieurs outils
de sécurité. Avant une collecte prolongée, définir une rétention limitée
pour Prometheus et contrôler les données. Les ports 3000, 9090 et 9100
doivent rester privés au laboratoire ; ne pas configurer de redirection
de ports vers Internet.


13. PERSPECTIVES D'AMELIORATION

  1. Réparer la relation Terraform/VM marquée tainted sans perdre les
     données, puis choisir un fournisseur VirtualBox maintenu ou une
     approche plus stable. Vérifier support et compatibilité avant
     migration.
  2. Persister la configuration réseau Ubuntu afin que eth1/NAT se
     réactive automatiquement au redémarrage.
  3. Rendre l'adresse de la VM stable (DHCP avec réservation ou adresse
     statique adaptée au réseau Host-only), puis gérer l'inventaire sans
     adresse codée en dur.
  4. Séparer noms de groupe et d'hôte Ansible et corriger les modules
     community.mysql dépréciés.
  5. Stocker les secrets Ansible dans Ansible Vault ou un gestionnaire
     de secrets et retirer la clé Vagrant publique du laboratoire.
  6. Protéger les secrets Apache et l'accès MariaDB, et contrôler les
     permissions de la configuration générée.
  7. Utiliser un agent Jenkins isolé plutôt que le contrôleur pour
     exécuter les builds, définir une politique de rétention et libérer
     l'espace disque sans supprimer JENKINS_HOME à l'aveugle.
  8. Ajouter une sauvegarde/restauration MariaDB et une procédure de
     retour arrière du déploiement.
  9. Versionner terraform/.terraform.lock.hcl, mais jamais state,
     tfvars, clé privée ou secret.
 10. Envisager un DNS local plutôt que de dépendre directement d'une IP.


14. CONCLUSION
-----------------------------------------------------------------------

Le laboratoire a permis de créer une VM Ubuntu VirtualBox, de la rendre
accessible depuis Kali par SSH, de configurer son réseau NAT/Host-only,
puis de déployer TaskManager avec Ansible. La réponse HTTP 200 et l'accès
MariaDB confirment que l'application fonctionne. Jenkins valide et
redéploie l'application ; Prometheus collecte maintenant les métriques
de Kali et Ubuntu, et Grafana interroge Prometheus avec un test de source
de données réussi.

La principale limite restante est la gestion Terraform : le fournisseur
a créé la VM mais a échoué en lisant les propriétés réseau de l'invité,
et l'état local marque actuellement la ressource "tainted". La priorité
est donc de sécuriser les données puis de corriger cette incohérence
avant toute nouvelle commande Terraform susceptible de remplacer ou
supprimer la VM.
